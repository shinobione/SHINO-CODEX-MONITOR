# CODEX PERISCOPE 5.2 Preview — concurrent turns and window icon P0

**Release decision: HOLD.** Integrates with Premium Polish in the existing Draft [PR #14](https://github.com/shinobione/SHINO-CODEX-MONITOR/pull/14), starting at `253ed48f8a78362d70bfc01682f0e3b22072c5df`. No other active Codex session on this checkout or remote-head movement was found at the initial inspection. The two pre-existing modified V5.1 batch launchers remain outside this change.

## What changed

- `LiveTaskReader` returns a collection of safely distinguishable turns, including distinct turn IDs within one root session. Identity combines the source session, UTC start ticks and the full validated turn ID; workspace labels are never identities. The old `ParseLines`/single-primary presentation APIs remain only for compatibility tests and redacted legacy diagnostics. The live widget consumes `MissionTracker` and `MissionDeck` instead.
- Each turn retains its own phase, start, confirmed finish, duration, model/effort and freshness. Contradictory/reused IDs and overlapping anonymous starts become UNVERIFIED, without inventing another mission. An anonymous terminal cannot finish two open turns. A unique anonymous start can acquire its ID from a subsequent valid, unambiguous context event. Missing sources remain UNVERIFIED, never completed.
- Distinct turns in one file do not borrow generic file freshness from each other. Explicit matching lifecycle/context records support per-turn freshness. File writes can support one uniquely open turn only if it does not overlap another known turn. Silence does not imply completion.
- Unchanged sources reuse sanitized snapshots, and a growing tail retains known start records. Reading remains bounded: 48 candidate headers, 12 root sessions, 512 KiB normal tails, 64 retained turns per session, 64 sanitized session caches. Cold recent roots share the existing total 16 MiB expansion budget, up to 4 MiB per root, rather than expanding only the freshest root. Old completed turns are evicted before new starts when the per-session limit is reached. Over-limit open turns remain uncertain. Header metadata is re-read after truncation. A reader lock protects caches during overlapping wake/cancel generations; no reader runs on the UI thread.
- One full-width card for one observed turn; equal cards for two; compact grid/scrollable list for three or more. The existing activity area and outer window geometry remain unchanged in Circular, Vertical, Compact and Micro. Card bounds use the native window DPI; tight cards fit the actual Micro height without hiding the metadata row. Each card has a safe label, status, elapsed/recorded duration and model/effort; full details are available through accessible descriptions/tooltips. Counts describe observed local turns, never guaranteed active Desktop missions.
- All cards reuse the Premium radar. One UI timer and one shared monotonic deck clock drive independent phase offsets and completion epochs. A's completion does not reset B's sweep, card identity or duration. Hidden/offscreen/inactive cards do not request graphical frames. Wake/starvation resets visual timing without replaying completion.
- Existing task-alert opt-in and confirmed-event rules remain. Notification keys now include the full turn identity; dedup entries persist for ten minutes instead of clearing the entire ledger at 256 entries. Quota parsing, alert thresholds, quota refresh cadence, history data and preference storage are unchanged.

## Taskbar icon investigation and correction

`Form.Icon`, native big/small HWND icons, the dynamic quota `NotifyIcon`, embedded executable resources and shortcuts are separate surfaces. Previously the form assigned its managed icon once, while `ShowInTaskbar` can recreate a handle. This is a concrete lifetime gap; it does **not** establish the complete historical cause of the user's shell icon regression.

`PeriscopeWindow` now loads the real embedded resource group at the current window DPI and explicitly applies **WM_SETICON** for big and small icons after handle creation, showing, display/DPI changes and visibility messages. It frees owned HICON resources after replacement/destruction. `MonitorForm` and `HistoryWindow` share this base. The taskbar icon is static and independent of the quota tray ring. The process does not rebuild the icon continuously or modify shell pins, registry startup entries or installation data.

Read-only local shortcut inspection found an existing **Codex Periscope** Start Menu shortcut targeting the retained `SHINO-CODEX-MONITOR.exe`, with the EXE's icon at index zero. No Periscope/legacy-monitor taskbar pin was found in the inspected user taskbar shortcut folder. An unrelated SHINOBIWAN LaunchPAD shortcut was left alone. No shortcut was changed, cache cleared or application reinstalled. Explorer's icon cache, other pin locations and behavior after reboot still require visual field checks.

## Tests and evidence

Baseline regression probes initially failed **0/3**: only the last of two turns survived, A's completion/active B was lost, and per-turn freshness was wrong. Candidate validation includes **25 new native P0 tests**, the existing **98 application**, **46 activity** and **35 Premium** tests, plus **122 Python audits** (118 previous + four collection/icon boundary guards).

P0 cases cover A+B active, either completion while the other continues, both short turns ending between polls, same workspace, distinct IDs in one session including equal start times, repeated terminal events, stale/missing sources, anonymous/contradictory IDs, startup/wake suppression, subagent exclusion, three turns, long IDs, context identity enrichment, growing-tail caching, two cold long sessions, bounded-cache rollover, independent completion animation, and one/two/three cards at the actual activity widths/heights of all four layouts. Label bounds are checked against card height, including the 92 px Micro activity area.

Native window checks build the actual EXE with `/win32icon`, create real HWNDs, query **WM_GETICON**, and pixel-check both small and big radar images across 20 cycles of hide/show, `ShowInTaskbar`, forced handle recreation, minimize/restore and display messages. Local finite-cycle counts were GDI **31 → 34**, USER **12 → 14**, within the asserted four-handle tolerance; this is not a long-running leak certification. Native window-frame and card images are labelled **SYNTHETIC TEST DATA**. Full shell taskbar/Alt+Tab confirmation remains a separate gate.

A test-harness initialization bug was found during this work: adding a card before assigning its mission let a layout callback dereference null. The user's exception screenshot identifies `MissionDeck.Arrange` and matches this test-harness failure. Cards are now initialized before insertion; the UI regression test exercises that path. P0 test modes use `UnhandledExceptionMode.ThrowException` so UI failures become test failures rather than modal .NET dialogs. The two affected test processes were terminated; a subsequent process check found only the pre-existing installed widget, left untouched.

## Performance observations

Synthetic native component measurement, no live readers, Windows NT 10.0.26300 on 12 logical processors: three independent radars, **635 frames / 30.25 s**, **20.99 FPS**, **0.758% total-machine CPU** / **9.09% of one core**. Hidden for five seconds: graphical timer disabled, **zero frames**, **zero running radar clocks**, CPU **0.000%** at measurement resolution. The sampler remains active during the benchmark.

Three batches of 100 deck resize/update/dispose cycles: private bytes **33,828,864 → 33,460,224**, **32,571,392 → 32,550,912**, **32,550,912 → 32,583,680**; GDI **19 → 19** each batch. This bounded test settles after warmup. It excludes installed-widget collection/notification costs and does not certify all hardware or physical DPI configurations. CI emits its own measurements, which may differ.

## Delivery and field gate

The Preview build requires P0 tests before packaging; Windows CI also runs the three-radar benchmark and uploads `P0_TEST_REPORT.txt`, `P0_PERFORMANCE_REPORT.txt`, progress diagnostics and annotated `p0-qa` images alongside the existing Premium evidence. App artifact: **CODEX-PERISCOPE-V5.2-PREVIEW-WINDOWS**. Evidence artifact: **CODEX-PERISCOPE-V5.2-SYNTHETIC-QA**. Installer validation remains `-ValidateOnly`; final ZIP must contain exactly seven allowlisted files and its EXE must match the tested SHA-256. This work leaves version **5.2 Preview** and the stable V5.1 paths intact.

**Required before release:** run two real Codex missions, complete either while observing the other, then complete the second; verify one justified notification each and silence with alerts disabled; visually confirm taskbar and Alt+Tab icons, history icon, pin/unpin and minimize/restore; test reboot and V5.1 upgrade on the user's PC with explicit installation consent; verify physical 100–200% / mixed monitor DPI and scrolling; confirm quota notifications, preferences/history preservation and long-running resource stability. These were not replaced by synthetic tests. No automatic installation, merge, tag, autostart change or public Release.
